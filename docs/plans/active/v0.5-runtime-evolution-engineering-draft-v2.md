# v0.5 Runtime Evolution — engineering draft v2

## Status and authority

This is a pre-implementation engineering plan. It is not an accepted
architecture document and it does not describe functionality that axiomos
currently provides. The implementation at the reviewed commit remains the
source of truth.

Before implementation, the lifecycle, publication, state, authority, ABI,
recorder, persistence, and replay decisions in this draft must be captured in
accepted ADRs and reflected in `docs/architecture/` as they land. Plans define
execution order; they do not silently become runtime contracts.

### Evidence update — 2026-07-29 HIL session (verified at this commit)

Three facts material to this plan changed at or just before the reviewed
commit and are folded into the gates below (G-13, new G-17) and the provenance
section. They were re-verified against the tree, not taken from a summary.

- **Builds are now bit-reproducible on the same host and toolchain.** The
  embedded ext2 rootfs (`build.rs`, `kernel/build.rs`) previously stamped a
  random `mke2fs` UUID, directory hash seed, and timestamp into the image
  compiled into the kernel, so three clean rebuilds of the identical tree
  produced three different `kernel8.img` hashes. Pinning `-U`,
  `-E hash_seed=`, and `SOURCE_DATE_EPOCH=0` (commit `664cd19`, the reviewed
  baseline) makes two `cargo clean` rebuilds byte-identical. This lets the
  provenance v2 gate **require rebuild-to-hash reproduction**, not merely pin an
  artifact hash. Cross-host/LLVM reproducibility is not yet proven.
- **Physical hardware-PWM actuation is blocked, not merely unmeasured.** The RP1
  `clk_pwm0` functional clock does not run on bare metal (xosc or a clock-tree
  dependency above it is ungated); the PWM counter never advances even with
  parent, gate, and divider registers confirmed correct by readback. All v0.3
  physical actuation to date is **GPIO-level**, via `guard_gpio` → `set_high/
  set_low`, not PWM. Any "motor/PWM output" corroboration in the benchmark
  matrix is currently impossible and is tracked as G-17.
- **v0.3 acceptance is partially closed with committed provisional evidence.**
  V03-A (monitor overhead, M-A median 37 ns) and V03-C (containment, 0 escapes
  on-device) pass; V03-B is measured (M-C median 4.500 µs software / 9.25 µs
  physical pad-to-pad, both over the < 1 µs target) at N ≈ 10,000; the raw UART
  logs are retained under `docs/performance/evidence/hil-v03-20260724/`. This
  evidence is **provisional**: the deployed images were `worktree_dirty = true`,
  so it does not satisfy the publication contract. With build determinism now in
  place, a clean rebuild + reflash can promote it to attributable. V03-D has a
  feature-gated harness (`bench-estop-rearm`) and a reproducible image, but the
  physical run is not yet done.

## Executive decision

**Do not begin broad v0.5 feature implementation yet.**

It is reasonable to begin the ADRs, control-cycle infrastructure, benchmark
oracle, trace schema, and issue cleanup now. It is not reasonable to promise
hot-swap, rollback, deterministic replay, a paper result, or production
readiness until the prerequisite gates in this document close.

| Decision | Status | Reason |
|---|---|---|
| Architecture and benchmark design | **Go** | These artifacts are prerequisites and can be developed without overstating implementation maturity. |
| Dedicated control-cycle and benchmark-oracle work | **Go with gate** | This is reusable infrastructure, but its timing contract must be accepted first. |
| Registry and atomic activation implementation | **No-go today** | Behavior identity, lifecycle, state ownership, authorization, and the publication linearization point are undefined. |
| Flight-recorder implementation | **No-go today** | “Post-run,” retention, persistence, loss behavior, schema, and replay fidelity are undefined. |
| v0.5 release claim | **No-go** | The feature does not exist, the local release gate is not green, and prerequisite HIL evidence is incomplete. |
| OSDI result claim | **No-go** | The v0.4 robot demonstration and attributable v0.5 evidence do not yet exist. A submission date is not an engineering gate. |

## Required architecture

### Behavior identity

Use distinct identifiers for distinct concerns:

- `BehaviorId`: stable logical identity, such as the wall-follow controller.
- `Revision`: signer-issued monotonic revision for that behavior.
- `ContentDigest`: cryptographic digest of the exact verified payload and
  immutable manifest.
- `ActivationGeneration`: kernel-issued monotonic number incremented on every
  activation and rollback.
- `OperationId`: correlation ID for one requested activation, rollback, retire,
  or failed transaction.

Do not use a program handle as behavior identity. Handles describe a live
kernel allocation and can be recycled safely through generations; they do not
express semantic lineage.

### Signed behavior manifest

The current signed-program header is insufficient. Define a canonical,
domain-separated manifest whose signature covers at least:

- manifest magic, format version, and signature algorithm
- `BehaviorId`, `Revision`, and payload digest
- full signer key fingerprint, not only an eight-byte display identifier
- map/state schema digests and declared mutability class
- hook/behavior-slot bindings
- physical capability and actuator-contract declaration
- helper policy and admission/WCET declaration
- compatibility floor/ceiling for kernel ABI and manifest format
- signer-provided creation time, if retained

Kernel load, activation, rollback, and retirement times are separate facts.
Record them with monotonic raw ticks and a boot/session ID. Wall-clock time may
be attached by trusted tooling, but it must not replace monotonic ordering.

For the first version, reject:

- duplicate or decreasing revisions except through the explicit rollback API
- unknown required manifest fields or nonzero reserved fields
- mismatched payload, map-schema, or contract digests
- unsigned registry metadata
- activation by a principal lacking behavior-administration authority

### Lifecycle

The minimal lifecycle is:

```text
                     register/verify
Candidate  ─────────────────────────────►  Resident
                                             │
                                             │ activate at cycle boundary
                                             ▼
                                           Active
                                             │
                    replace with B            │ retire active is illegal
              ┌───────────────────────────────┘
              ▼
     Resident A + Active B
              │
              │ rollback to exact retained A
              ▼
     Active A + Resident B

Resident ── retire ──► Retired metadata + reclaimable runtime
```

Rules:

1. A behavior slot has exactly one Active activation generation.
2. Registration and verification perform allocation and expensive work outside
   the control-cycle commit path.
3. Active and retained rollback revisions are kernel-owned, independent of the
   loader PID.
4. Rollback creates a new `ActivationGeneration`; it does not rewind history.
5. History is an immutable event sequence. Do not maintain a second mutable
   “history” view that can disagree with lifecycle state.
6. Retiring the Active revision is invalid. The caller must activate another
   Resident revision or enter an explicit safe/no-behavior state first.
7. The v0.5 retention minimum is the current Active revision plus its exact
   previous successful revision. Retention limits and eviction must be
   queryable and deterministic.
8. Shadow, automatic promotion, verified migration, and contract-subtyping are
   not v0.5 lifecycle states.

### Atomic activation transaction

The proposed phrase “wait one grace period, flip the versioned pointer” should
not be implemented literally.

Conventional RCU does this:

```text
prepare replacement -> publish pointer -> grace period -> reclaim old snapshot
```

The robot-control requirement is stronger. It needs cycle quiescence:

```text
prepare and admit outside real-time path
    -> queue transition with expected generation
    -> current control cycle exits
    -> atomically publish at the cycle boundary       [commit point]
    -> next eligible cycle enters the new generation
    -> reclaim obsolete dispatch snapshot after grace
```

The old program runtime remains Resident because the registry owns a strong
reference. That is independent of when an obsolete dispatch snapshot is
reclaimed.

The transaction must:

1. Authenticate a narrow behavior-administration capability.
2. Resolve an already verified Resident target.
3. Compare the caller's expected Active generation.
4. Validate state compatibility, hook bindings, physical contract, helper
   policy, and resource/WCET delta.
5. Reserve every allocation and lifecycle/recorder record before commit.
6. Build the complete next immutable dispatch generation.
7. Serialize competing lifecycle writers.
8. Commit once at a named control-cycle boundary.
9. Emit `ActivationCommitted` with the old/new generation and operation ID.
10. Allow the next eligible cycle to execute the new generation.
11. Complete snapshot reclamation asynchronously and emit
    `GraceCompleted`.

Any failure before commit leaves the old behavior Active and resource charges
unchanged. No fallible work belongs between commit and the next behavior
entry. A stale expected generation returns a stable stale/conflict error rather
than silently replacing a newer behavior.

### Rollback contract

Manual rollback must call the same atomic activation primitive. It is not
detach plus reattach.

The caller identifies:

- the expected current `ActivationGeneration`
- the exact prior activation/history entry to restore

The kernel verifies that the retained target has the same digest and signer
recorded in history, creates a new activation generation, and commits at a
cycle boundary. It must not reload, allocate, parse, or reverify bytecode on
the real-time path.

Rollback does not:

- restore arbitrary private mutable maps
- clear a latched e-stop
- bypass current physical safety policy
- downgrade to an arbitrary older revision outside retained history
- imply automatic fault detection or automatic rollback

Repeated rollback and rollback-of-rollback semantics must be explicit. The
recommended API targets an exact history entry instead of toggling an implicit
two-element stack.

### State compatibility

“No missed cycle” does not imply a bumpless physical transfer. A PID integrator,
filter, estimator, or MPC warm state can cause a discontinuity even when
dispatch changes atomically.

Because verified migration is deferred, v0.5 should support only:

1. stateless behaviors; or
2. state stored in a kernel-owned interface whose schema and semantics are
   explicitly stable across both revisions.

Private mutable map transfer, shared writable state with unclear ownership, and
in-place schema changes are rejected. A later migration system can expand this
contract after it has verification, rollback, and bumpless-transfer semantics.

### Authority and failure policy

- Loading a correctly signed program proves origin; it does not grant authority
  to activate it.
- Add a least-privilege behavior-administration capability for register,
  activate, rollback, retire, and history operations.
- Preserve the full signer fingerprint and authorization principal in every
  lifecycle event.
- E-stop always dominates activation and rollback. A swap can change code while
  outputs remain safe, but it cannot rearm motion.
- Recorder or persistence failure must never block the control loop. Management
  operations can fail before commit if their required lifecycle event cannot be
  reserved.
- A stalled read-side participant must produce a bounded diagnostic. It must
  not leave a writer spinning forever with interrupts or the control executor
  unavailable.
- Registry quotas must cover resident runtime bytes, history, maps, recorder
  reservation, and per-principal behavior counts.

### ABI shape

Add versioned request/response structures rather than expanding `BpfAttr`:

- `behavior_register`
- `behavior_query`
- `behavior_list`
- `behavior_activate`
- `behavior_rollback`
- `behavior_retire`
- `behavior_history`
- `recorder_query`
- `recorder_read` or `recorder_export`

Every structure needs:

- `size` and `version`
- reserved-zero fields
- explicit string/blob lengths
- stable identifiers rather than internal pointers
- pagination/cursor semantics for lists and history
- deterministic `ESTALE`, `EBUSY`, `EINVAL`, `EPERM`, `ENOSPC`, and timeout
  behavior
- old-caller and new-kernel compatibility tests

|---|---|---|
| Bounded run recorder | Reconstruct activation history and commanded/applied actuation after a normal run while data remains available | Versioned records, loss accounting, export ABI, asynchronous drain |
| Crash flight recorder | Recover an ordered valid prefix after crash/reboot or power loss | Preallocated durable storage, integrity framing, recovery scanner, loss-window bound, power-cut campaign |
| Deterministic behavior replay | Re-execute the recorded run and reproduce behavior outputs | All behavior inputs, nondeterministic helper results, relevant state/checkpoints, execution order, replay engine, equality oracle |

**Recommendation:** ship the bounded recorder foundation in v0.5 and say
“reconstruct what the robot commanded.” Retain “replay what it did” only if the
deterministic replay row is funded and accepted. Calling a volatile,
overwrite-oldest ring a flight recorder would be misleading.

#### Product recorder architecture

Use fixed-size, versioned binary records in preallocated per-CPU single-writer
buffers. Do not put allocation, formatting, serial output, filesystem I/O, or a
contended mutex in the producer path. A background task may merge and batch
records into preallocated append-only segments.

Avoid a global atomic sequence on every hot-path event unless measurement proves
it harmless. Per-CPU sequence numbers plus global control-cycle and operation
IDs can establish causality without central contention.

Each record needs the applicable subset of:

- schema version and event type
- boot/session ID
- per-CPU sequence, CPU ID, and monotonic raw counter tick
- control-cycle sequence and operation/correlation ID
- `BehaviorId`, `Revision`, digest reference, and `ActivationGeneration`
- signer/authorization reference for lifecycle events
- requested, decided, and actually applied value
- monitor outcome, clamp/reject reason, physical route, and application result
- activation, rollback, retirement, e-stop, recorder-gap, and recovery events
- block length and CRC/integrity field for persisted segments

Buffer exhaustion never blocks control. It increments an explicit loss counter
and emits a gap record when recording resumes. The release benchmark still
requires zero gaps at the declared design and headroom rates.

The current actuation audit ring can remain a small monitor-local diagnostic,
but it must not be the only product recorder or the benchmark oracle.

## Benchmark protocol v2

### Benchmark principles

The current three bullets are not sufficient acceptance criteria. They omit the
clock, event boundaries, sample population, load conditions, tail statistic,
confidence rule, record size/rate, loss policy, and independent oracle.

The v0.5 benchmark must:

1. measure a named 1 ms absolute-deadline control period;
2. separate prepare, commit, first execution, and grace completion;
3. prove transition integrity with cycle and generation IDs;
4. keep measurement output out of the timed path;
5. use an independent benchmark oracle rather than trusting the recorder under
   test;
6. correlate kernel evidence with externally captured physical markers;
7. fail closed on missing, malformed, truncated, reordered, or insufficient
   evidence;
8. report per-boot results before pooled statistics; and
9. describe zero observed failures as a bounded observation, not a proof of
   universal absence.

### Fixed timing contract

Define:

- `P = 1,000,000 ns`
- `cycle_seq`: contiguous sequence assigned by the dedicated control dispatcher
- `t_request`: first kernel timestamp after copying the fixed-size activation
  request and before authorization, lookup, compatibility, or boundary wait
- `t_accept`: activation has passed authorization, lookup, compatibility, and
  resource preparation and is queued for the next eligible boundary
- `t_commit`: the active dispatch generation changes atomically
- `t_enter`: first instruction of the new generation for its first eligible
  control cycle
- `t_grace`: obsolete dispatch readers have drained; this is not the activation
  visibility point

Required events:

```text
CycleRelease(cycle_seq, scheduled_tick, actual_tick)
ActivationRequested(operation_id, expected_generation, target_revision, tick)
ActivationAccepted(operation_id, old_generation, new_generation, tick)
ActivationCommitted(operation_id, old_generation, new_generation, tick)
GraceCompleted(operation_id, old_generation, tick)
BehaviorEnter(cycle_seq, generation, tick)
BehaviorExit(cycle_seq, generation, tick, status)
CycleComplete(cycle_seq, tick)
RollbackAccepted(...)
RollbackCommitted(...)
RecorderGap(cpu, first_missing_seq, count, tick)
```

Primary metrics:

| Metric | Definition | Why it exists |
|---|---|---|
| End-to-end activation latency | `first BehaviorEnter(new).tick - ActivationRequested.tick` | Primary, non-gameable kernel-entry-to-use latency |
| Accepted activation latency | `first BehaviorEnter(new).tick - ActivationAccepted.tick` | Boundary wait plus dispatch visibility |
| Activation preparation latency | `ActivationAccepted.tick - ActivationRequested.tick` | Authorization, lookup, compatibility, and reservation cost |
| Commit latency | `ActivationCommitted.tick - ActivationAccepted.tick` | Management and boundary-wait cost |
| Publication-to-use latency | `first BehaviorEnter(new).tick - ActivationCommitted.tick` | Dispatch visibility at the control executor |
| Grace latency | `GraceCompleted.tick - ActivationCommitted.tick` | Reclamation health; not activation latency |
| Release jitter | `CycleRelease.actual_tick - CycleRelease.scheduled_tick` | Timer/executor quality |
| Cycle service time | `CycleComplete.tick - CycleRelease.actual_tick` | Control-path execution cost |
| Deadline slack | `scheduled_tick + P - CycleComplete.tick` | Direct deadline margin |
| Recorder paired delta | `latency_on - latency_off` for a matched trial | Recorder observer effect |

Do not define activation latency from syscall return. Do not define it from load
or signature verification, because v0.5 hot-swap is specifically activation of
an already verified Resident revision. Registration/verification latency is a
separate benchmark.

### Acceptance rows

Freeze these in a machine-readable `benchmarks/v05/acceptance.toml` before the
paper campaign. If that location is adopted, create the directory and make it
the single authority rather than duplicating thresholds in prose and scripts.

| ID | Claim | Acceptance |
|---|---|---|
| V05-A | Register and verify | Report latency and memory charge by payload size, instruction count, map count, and signer path. No hot-swap threshold is inferred from this row. |
| V05-B | Activation latency | For an already verified Resident target, observed maximum `t_enter - t_request < P`, observed maximum `t_enter - t_accept < P`, and the new generation executes no later than the next logical control cycle. Report request, preparation, commit, publication-to-use, and grace distributions separately at p50/p95/p99/p99.9/p99.99/max per boot and pooled. |
| V05-C | Transition integrity | Every scheduled cycle executes exactly one generation. Zero missing, duplicate, mixed-generation, out-of-order, or externally missing cycles in at least 1,000,000 measured cycles per workload/condition. |
| V05-D | Manual rollback | Restore the exact retained revision—same digest and signer—without reload, allocation, or reverification in the commit path. Meet V05-B and V05-C again. |
| V05-E | Recorder overhead | In same-image paired ABBA trials, the upper 95% confidence bound of median relative overhead is below 5%, and `p99_on <= 1.05 × p99_off`. Also report absolute nanoseconds, deadline slack, CPU cost, bytes/event, and timestamp cost. Zero deadline misses and unreported loss. |
| V05-F | Recorder throughput | Let design rate be the frozen maximum records/cycle multiplied by 1 kHz. With the provisional two-motor schema this is 4,000 events/s. Sustain at least 2× design rate—provisionally 8,000 events/s—for ten minutes with zero gaps/drops, and report maximum sustainable events/s and bytes/s. |
| V05-G | Churn and reclamation | At least 100,000 activate/rollback/retire operations with resident bytes, snapshot backlog, handle count, and registry history within declared bounds; stale handles always rejected. |
| V05-H | Crash persistence | Required only if claimed: after randomized power cuts, recover a valid ordered prefix with no silent corruption and no more than the declared maximum loss window. |
| V05-I | Deterministic replay | Required if “replay what it did” remains: replay all captured inputs/nondeterminism/state and reproduce every behavior output and applied actuation record exactly. |

A million clean cycles means “zero observed in 1,000,000.” Under the simple
rule-of-three approximation, the 95% upper bound remains roughly three failures
per million. A paper campaign should raise continuity runs to at least ten
million cycles per workload/condition, reducing that bound to roughly
0.3 per million.

### Transition invariants

A missed or invalid cycle is any:

- absent or duplicate `cycle_seq`
- completion after the absolute deadline
- missing external cycle/completion marker
- cycle with zero or more than one behavior generation
- old-generation `BehaviorEnter` after commit
- out-of-order release, entry, exit, or completion event

Because this draft recommends quiescence before the cycle-boundary commit, an
old-generation exit after commit is also a failure.

The same invariants apply to rollback. E-stop trials additionally require safe
physical output throughout the transition and prove that rollback did not clear
or bypass the latch.

### Instrumentation

Use two independent evidence planes.

#### Benchmark oracle

- benchmark-only preallocated per-CPU fixed-record buffers
- one writer per buffer
- raw `CNTVCT_EL0` ticks and recorded `CNTFRQ_EL0`
- no allocation, formatting, serial, generic logging, storage I/O, or contended
  lock in a measured path
- drain only after the measured interval
- retain and report timestamp-read cost; do not subtract it from acceptance

#### Product recorder

This is the recorder being measured. It cannot be the sole oracle for its own
correctness, loss rate, or overhead.

UART is limited to start/end control markers during a measured interval. The
existing v0.3 pattern that formats and writes serial telemetry before the
physical actuation must not be reused.

#### External corroboration

Use RP2040 PIO or FPGA edge-timestamp capture instead of storing continuous
high-rate logic-analyzer samples for every long run. Capture:

- independent 1 kHz release/reference
- control-cycle completion
- distinct harmless generation A/B marker
- representative motor/PWM output — **blocked while G-17 is open**; the RP1 PWM
  counter does not run on bare metal, so this corroboration is GPIO-level output
  only until the RP1 clock manager is brought up

Require at least 10,000 externally observed activation/rollback transitions for
each recorder mode and behavior workload. Record analyzer model, serial,
firmware, calibration, wiring, clock, and capture configuration.

### Campaign matrix

Run a clean reproducible Pi5 image over **ten cold boots**.

Workloads:

1. dispatch-only Resident behavior
2. `forward_drive` two-actuator path
3. sensor/map/branch-heavy `wall_follow`
4. maximum-admitted-WCET behavior

Conditions:

1. otherwise idle
2. CPU/cache/memory contention on other available cores
3. IRQ/I/O plus recorder-flush pressure
4. epoch stress with readers on every eligible CPU

If Pi5 SMP remains incomplete, condition 2 and the all-CPU reader claim are not
valid substitutes for SMP evidence. Record them as unsupported rather than
silently running only one core.

Minimum populations:

- activation: 100,000 operations per workload/condition, with at least 10,000
  per boot
- rollback: the same
- activation phase: populate 100 bins across `[0, P)` so requests are not
  accidentally synchronized to an easy boundary
- transition continuity: 1,000,000 measured cycles per workload/condition;
  10,000,000 for paper evidence
- recorder overhead: 1,000,000 cycles per recorder mode/workload/condition
- recorder throughput: ten minutes at design and 2× headroom, then five
  60-second repetitions at 1×, 2×, 4×, and 8× design rate

Use one image and balanced ABBA ordering (`off/on/on/off`) for recorder cost.
Do not compare separately optimized binaries. Tag and retain an explicit 10,000
cycle stabilization phase before `MeasureStart`; do not delete the first N
measured samples after inspecting them. Every boot must pass independently
before pooled results are considered.

### Adversarial and fault campaigns

At minimum:

- concurrent activation and rollback writers
- expected-generation race and stale request
- reader spanning a boundary on each CPU
- deliberately stalled reader longer than one period
- empty history, invalid target, and repeated rollback
- preparation allocation or admission failure
- recorder full, flusher failure, storage full, and recovery
- e-stop asserted before, during, and immediately after commit
- loader PID exit while revisions are Resident and Active
- counter, sequence, handle-generation, and activation-generation wrap
- 100,000-operation churn with memory/snapshot backlog required to plateau
- malformed, truncated, reordered, duplicated, and CRC-corrupt recorder input

The stalled-reader outcome must be chosen by the ADR. Under the recommended
cycle-quiesced design, a transition that cannot reach the boundary fails before
commit and leaves the old behavior Active. It must not spin forever or expose a
half-published generation.

### Reducer and provenance

The current provenance verifier is a useful artifact-hash foundation:
[`benchmark-provenance.py`](../../../scripts/verify/benchmark-provenance.py).
The stricter reducer pattern is
[`v03d-reduce.py`](../../../scripts/hil/v03d-reduce.py). Do not copy the
fail-open behavior in [`v03b-reduce.py`](../../../scripts/hil/v03b-reduce.py),
which can exit successfully when the sample population is too small or a target
is exceeded.

Create one strict v0.5 reducer. It must exit nonzero on:

- missing, duplicate, or out-of-order event/cycle sequence
- expected/observed count mismatch
- malformed/truncated record, unknown schema, or CRC failure
- raw-counter or monotonic-time reversal
- any deadline, generation, or transition violation
- any recorder gap/drop at an acceptance rate
- insufficient samples, cold boots, conditions, or phase-bin coverage
- any per-boot failure even if pooled data passes
- build/configuration/artifact hash mismatch
- undocumented filtering or exclusion

It should emit canonical `results.json` and generated Markdown containing:

- per-boot and pooled p50/p95/p99/p99.9/p99.99/max
- boot-stratified bootstrap 95% confidence intervals
- paired recorder on/off deltas and ratios
- raw and filtered counts with every exclusion reason
- design rate, record size, byte rate, drop/gap count, CPU cost, and capacity

The provenance manifest v2 should include:

- exact commit and tree hash with `worktree_dirty=false`
- build commands, target, profile, sorted features, and allow-listed environment
- toolchain/LLVM versions and hashes of lock, toolchain, and acceptance files
- kernel, rootfs, disk, trusted-key, manifest, and behavior payload hashes
- Pi serial/revision, firmware, RAM, clocks, temperature/throttle state, and
  power supply
- RP2040/FPGA source, firmware/bitstream hashes, and wiring map
- analyzer model/serial/firmware, sample rate, and calibration
- run/boot IDs, seed, `P`, expected counts, workload, and phase schedule
- every trace, UART log, external capture, result, and reducer artifact with
  role, size, and SHA-256
- reducer command, source hash/version, and verdict

The verification gate must rerun the reducer and require byte-identical
`results.json`. Checking only that a result file and its hash exist does not
reproduce the result.

Because kernel images are now bit-reproducible on the same host and toolchain
(see the 2026-07-29 evidence update), the gate should additionally require a
clean rebuild at the recorded commit to reproduce the recorded `kernel8_sha256`
exactly. An image whose manifest records `worktree_dirty = true` cannot be
reproduced and its evidence stays provisional regardless of how completely its
hashes are recorded. Cross-host reproduction is not yet claimed; the toolchain
and LLVM hashes in the manifest bound that gap.

### Benchmark-tool tests

Before accepting HIL evidence:

- golden valid and corrupt traces
- missing, duplicate, and reordered sequence IDs
- truncation at every record/block boundary
- sequence/counter/generation wrap
- deterministic multi-CPU merge ordering
- percentile and confidence-interval tests against synthetic distributions
- fuzzing for parser and reducer
- Loom models for atomic publication, concurrent rollback, and recorder
  append/drain
- storage-full and flusher-failure injection
- external capture loopback with a known programmed delay
- static measured-call-graph check forbidding serial, formatting, allocation,
  storage I/O, and blocking locks

## Open decisions

These are blocking design choices, not implementation details.

| Decision | Recommended v0.5 choice | Consequence if postponed |
|---|---|---|
| Behavior granularity | One registry-managed behavior bundle/slot with a declared set of hooks and physical outputs | A single “version” may replace only part of a controller and make rollback non-atomic. |
| Control executor | One designated 1 kHz executor; multicore work can prepare candidates but cannot split one actuation cycle | “No mixed version” becomes much harder to define and prove. |
| Commit semantics | Old cycle exits, one pointer/generation CAS at boundary, new starts next eligible cycle | Existing RCU overlap permits ambiguity between publication and old-reader completion. |
| Mutable state | Stateless or stable kernel-owned state only | Reattaching old bytecode is falsely called rollback. |
| Previous-version retention | At least exact prior successful activation, bounded and queryable | Rollback can fail due to implicit eviction or process exit. |
| Activation authority | Dedicated least-privilege capability distinct from signed load | Any loader of trusted code may alter live robot behavior. |
| Persistence | Explicitly choose normal-stop RAM export or crash/reboot durability | “Flight recorder” has no testable meaning. |
| Replay | Fund complete deterministic replay or reduce wording to causal reconstruction | The release and paper overclaim available evidence. |
| SMP scope | Close #59 or declare one control executor and no Pi5 SMP result | Four-core RCU claims remain unsupported. |
| Actuation output | Scope v0.5 physical actuation to GPIO-level until G-17 (RP1 PWM clock) is resolved; do not assume hardware-PWM | A benchmark that assumes motor/PWM corroboration cannot produce it, and the "applied actuation" record silently means GPIO-level. |
| Publication target | Treat OSDI as a calendar target; make artifact evidence the gate | Schedule pressure can redefine incomplete evidence as acceptance. |
