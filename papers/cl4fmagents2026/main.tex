\begin{abstract}
An embodied agent can improve a controller while remaining unreliable at installing it. Atomic publication selects one current program, but does not by itself prevent old and new invocations from overlapping. We define an executor-level installation contract combining expected installation identity, invocation quiescence, stateless admission, authority revalidation, and resource-atomic publication. A prototype implements this contract for one opt-in runtime slot using a nonblocking transition gate. We compare it with atomic publication sharing the same manager checks, accounting, and receipts, under matched failures and concurrent invocation. Across nine matched scenarios, atomic publication exposes one old/new-guard overlap; guarded replacement exposes none. Both preserve the predecessor on six rejecting requests. Hosted measurements separately quantify replacement and guard costs, retries, skipped dispatches, and retained bytecode. A deterministic payload-shift replay separately measures tracking quality and installation defects under a frozen gain-update sequence. Foundation-model adaptation, downstream command fencing, and physical safety remain outside the evaluated contract.
\end{abstract}

\section{The update is part of the execution contract}
\label{sec:position}
An agent revises a motor reflex after a payload change. Its candidate passes isolated tests, but activation races an old invocation whose queued command arrives later. A stale recovery request may also replace a newer installation that reuses the same program handle. These are installation failures, independent of controller quality.

Executable skills are one concrete adaptation medium: Voyager, for example, grows a library of programs using environmental feedback \citep{wang2023voyager}. Physical control adds restricted authority, deadlines, and effects that software rollback cannot undo. Our thesis is: \emph{adaptation should not imply deployment}. A candidate becomes authoritative only through a specified transition whose concurrency, identity, state, and accounting rules can be tested.

Qin et al. govern capability versions through compatibility checks, sandbox/shadow evaluation, gated activation, monitoring, rollback, and audit \citep{qin2026governed}. LITHE atomically swaps controller pointers at the end of a Spine cycle: its single loop supplies implicit quiescence, while state persists in shared memory \citep{lim2026lithe}. Kitsune supplies state-preserving dynamic software updating \citep{hayden2014kitsune}. Our narrower question concerns concurrent invocation, resource ownership, and stale requests at an executable hook boundary.

Action assurance is complementary: shielding constrains learner actions \citep{alshiekh2018shielding}, while Neural Simplex combines runtime assurance and online retraining \citep{phan2020neural}. An action monitor asks whether a command may execute; publication determines which installation may issue it. Evaluation should distinguish these obligations.

Our contributions are: (1) an executor-level contract combining expected installation identity, invocation quiescence, state admissibility, authority revalidation, and resource-atomic publication; (2) an implementation for one exclusive slot using a nonblocking transition gate and monotonic epochs; and (3) a comparison with atomic publication sharing the same manager checks, reporting correctness and hosted availability costs separately; and (4) a simulated payload-shift replay separating task quality from installation correctness.

\section{A narrow transactional publication primitive}
\label{sec:semantics}
A bare-metal Rust research kernel supplies verified runtime programs, load authentication, capabilities, quotas, and immutable snapshots. We add one opt-in exclusive TIMER slot. Ordinary TIMER fanout remains outside its gate; exclusivity concerns this slot. \emph{Transactional} denotes software-authority publication, without atomic physical effects or persistent recovery.

An installation is identified by
\begin{equation}
 I=(h,e), \qquad e\in\{1,\ldots,2^{64}-1\},
\end{equation}
where $h$ is a program handle and $e$ increases at every successful replacement, including rollback. Replacement checks the expected full $I$, preventing a stale request from becoming current when the same handle is reinstalled (ABA). Epoch exhaustion rejects; bootstrap is separate.

Invocation and replacement share one atomic state: open, active, or transitioning. Invocation claims open$\rightarrow$active, holds its snapshot guard throughout execution, and drops it before reopening. Other entry attempts return \textsc{TransitionBusy} or \textsc{ExecutionBusy} and increment skip counters. Replacement tries open$\rightarrow$transitioning once; an active invocation causes immediate, unchanged \textsc{Busy} rejection.

\textsc{Stateless} admits only candidates without verifier-reported runtime-map references. Map-bearing candidates and state transfer reject before gate acquisition. The internal enum \texttt{Reset} performs no clearing and makes no claim about device or external state.

Once quiescent, replacement checks expected identity, ownership, retained authentication provenance, bootstrap authority ceiling, TIMER re-verification, conflicts, and quota. It does not reauthenticate. Fallible snapshot preparation precedes mutation; a final serialized emergency-stop check rejects stop state or lock contention unchanged. The immutable published object contains runtime and full identity. The manager commits an allocation-free admission delta $-\mathrm{cost}(A)+\mathrm{cost}(B)$, publishes once, and records the receipt before reopening. Invocations read the object; serialized manager operations cannot observe intermediate ledger or receipt state. Both programs retain resident-memory charges. Rollback conditionally reinstalls the resident predecessor with a fresh epoch.

\paragraph{Two invariants.}
Assume serialized manager operations, normal returns, and invocations that hold their slot guard throughout their body. \emph{Invocation exclusivity:} if replacement from $I_A$ to $I_B$ succeeds, no guarded invocation of $I_A$ overlaps one of $I_B$. Entry claims open$\rightarrow$active; replacement claims open$\rightarrow$transitioning on the same atomic state. These claims exclude one another. Replacement publishes $I_B$ while transitioning, rejects new entries until completion, and reopens only with $I_B$ current. An old reader drops its snapshot before reopening. A successful invocation linearizes at its open-to-active transition; replacement linearizes at the pointer swap of the complete installation object.

\emph{Returned-error preservation:} every replacement returning an error preserves the published installation, executable snapshot, and admission ledger. All rejecting checks and snapshot preparation precede mutation. Ledger commit validates before writing; after it succeeds, publication and receipt updates have no error return. Releasing an unsuccessful transition only reopens the gate. This proposition excludes diagnostic counters, panic/crash recovery, and physical effects.

Receipts and diagnostic guard observations carry installation identity; production dispatch and actuation audit do not yet propagate it downstream.

\section{Correctness and availability under matched updates}
\label{sec:evaluation}
\paragraph{Same-manager comparison.}
\textbf{Atomic publication} (AP) and \textbf{guarded replacement} (GR) share validation, expected identity, ownership, authority, re-verification, accounting, snapshot preparation, and receipts. AP bypasses only the invocation gate through a host diagnostic path absent from bare-metal builds. Both publish the same immutable identity/runtime object. AP retains the predecessor allocation and waits for old readers before returning, but B becomes visible during that wait. A B reader can therefore overlap an A reader. GR returns \textsc{Busy} while A is active; a later retry can publish B. Each fixture fixes its protocol until draining cleanup.

Hand-written map-free bytecode uses unsigned development loading, so authentication is not tested. Hosted callbacks hold real guards without privileged bytecode execution or actuation. The admission model assigns 1\,kHz hook frequency and 500\,ms/s CPU budget; unrelated reservations exercise that budget. Fixture charges are measured through manager attachments, not execution timing. A separate QEMU probe checks interpreter dispatch after A--B--A and stale-request rejection.

\paragraph{Fault schedules.}
Both protocols receive snapshot-preparation failure, over-budget, authority, stale-identity, retry, ABA, rollback, and concurrent-proposer schedules. Rejections preserve snapshot, identity, ledger, and receipt. One schedule retains A, starts replacement, and attempts a B invocation. AP exposes B before A drains; GR rejects until A drains. Overlap records carry identities captured by actual guards. Accounting is checked outside callbacks: taking the manager lock while AP waits for a reader would deadlock.

\paragraph{Installation-conditioned control replay.}
An eight-second host simulation integrates $m\dot v=u-v$ by 100\,$\mu$s Euler steps, with mass $1\rightarrow2$ at four seconds and reference alternating $\pm1$ each second. Control ticks every millisecond use $u=\mathrm{clip}(k(r-v),-4,4)$. A seed tuner, starting at $k=1$, doubles gain up to 16 when recent 250\,ms tracking RMSE exceeds 0.1, at 4.25, 4.5, 4.75, and 5 seconds. We freeze these proposals before replaying frozen control, AP, and GR.

Real manager installations and guards select the gain; host code computes control. Each invocation captures identity and error at entry and applies its command at completion, with zero-order hold between commands. Normal holds are 100\,$\mu$s; one predecessor invocation at 4.249\,s lasts 2\,ms. Completion precedes update attempts, then control ticks. Each proposal has the same primary and $+1$\,ms attempt; AP can expose B while A remains held, whereas GR must retry. RMSE includes skipped ticks. Paired synchronous utility probes compare candidate and predecessor gains from the same activation state over 250\,ms; they do not estimate a learning algorithm's performance.

\section{Scope and implications}
\label{sec:limits}
Quiescence serializes invocations and trades availability for rejection; acceptability depends on the controller and schedule. Retaining predecessors costs memory; stateless admission excludes useful updates. Middleware could enforce this contract. AP is a manager ablation, not LITHE, whose single loop supplies cycle-boundary quiescence.



The contract ends at the guarded invocation. Commands can outlive their installation; physical motion cannot be rolled back. Queue fencing requires propagated identity and a stale-command rejection point. Controller stability, state transfer, persistent recovery, hardware-stop timing, and foundation-model continual learning require separate experiments. The replay illustrates two evaluation axes, without a robot or privileged controller execution: adaptation should not imply deployment.
