\begin{abstract}
An embodied agent can improve a controller while remaining unreliable at installing it. A candidate can pass isolated checks yet overlap an invocation of its predecessor, inherit incompatible state, or be activated against a stale version. Existing work already governs capability lifecycles and atomically hot-swaps robotic control laws. We therefore make a narrower claim: a runtime that exposes replaceable executable hooks should specify publication semantics at the invocation boundary. We describe one opt-in kernel TIMER slot with nonblocking, fail-closed replacement, explicit installation identity, a map-free state policy, and resource-accounting updates committed with publication. In five matched software scenarios, two-step replacement exposes three multi-version snapshots or five empty snapshots; guarded replacement exposes neither and preserves its predecessor on both injected failures. A separate snapshot-component ablation demonstrates overlapping old/new guards despite a single current pointer. These results isolate installation correctness from adaptation quality; learning quality, downstream command fencing, hardware reset, and physical safety remain unevaluated.
\end{abstract}

\section{The update is part of the execution contract}
\label{sec:position}
Consider an agent that revises a motor reflex after a payload change. The new controller passes isolated tests, but activation races an invocation of the old controller. A queued command from that invocation may reach the motor after the new controller becomes current. Alternatively, a stale recovery request may replace a later installation that happens to reuse the same program handle. These are installation failures, independent of whether the candidate is a better controller.

Executable skills are one concrete adaptation medium: Voyager, for example, grows a library of programs using environmental feedback \citep{wang2023voyager}. Physical control adds restricted authority, deadlines, and effects that software rollback cannot undo. Our thesis is: \emph{adaptation should not imply deployment}. A candidate becomes authoritative only through a specified transition whose concurrency, identity, state, and accounting rules can be tested.

This thesis complements established mechanisms at adjacent layers. Qin et al. treat a new capability version as a governed candidate and define compatibility checks, sandbox and shadow evaluation, gated activation, monitoring, rollback, and audit \citep{qin2026governed}. LITHE loads a new C++ controller off the real-time path, then atomically swaps its function pointer at the end of one Spine cycle, where the single Spine loop supplies implicit quiescence; controller state is deliberately kept in a persistent shared-memory block \citep{lim2026lithe}. Dynamic software updating also supplies state-preserving program replacement, as in Kitsune \citep{hayden2014kitsune}. We focus beneath lifecycle policy and beside these update mechanisms: what should an opt-in kernel hook guarantee when concurrent invocation, resource ownership, and stale replacement requests are visible at that boundary?

Action-level assurance remains separate. Shielding can constrain learner actions \citep{alshiekh2018shielding}, and Neural Simplex combines runtime assurance with online controller retraining \citep{phan2020neural}. An action monitor asks whether a command may execute in the current state. Publication asks which program installation is allowed to issue the next command. Either layer may reveal a failure the other cannot, so evaluations should report both rather than treating one as a proxy for the other.

\section{A narrow transactional publication primitive}
\label{sec:semantics}
Our case study is an anonymous bare-metal Rust research kernel with verifier-accepted runtime programs, authenticated load policy, capability checks, quotas, generation-tagged handles, and immutable hook snapshots. We add one opt-in exclusive TIMER slot; ordinary TIMER fanout still coexists and executes outside this gate. Exclusivity and skipped invocations refer only to the opt-in slot, not all TIMER programs or hardware access. The word \emph{transactional} refers only to publication of software authority at this slot. It does not imply atomic physical effects, persistent logging, or a general dynamic-update subsystem.

An installation is identified by
\begin{equation}
 I=(h,e), \qquad e\in\{1,\ldots,2^{64}-1\},
\end{equation}
where $h$ is a program handle and $e$ is a monotonically increasing installation epoch. Replacement is a compare-and-swap-style operation on the expected $I$, not just $h$. It publishes a fresh epoch at every successful replacement, including rollback, so removing and later reinstalling the same handle does not make an old request current (the ABA case). Epoch exhaustion rejects the transition. Bootstrap is a separate operation.

Invocation and replacement share one atomic state: open, active, or transitioning. An invocation atomically claims the open state; a transitioning state returns \textsc{TransitionBusy}, and an active state returns \textsc{ExecutionBusy}. Both failures increment explicit skipped-invocation counters. The invocation holds the immutable snapshot guard throughout execution and drops that guard before reopening the slot. A replacement tries to change open to transitioning once. If an invocation is active, it returns \textsc{Busy} immediately and leaves the slot unchanged; it never waits for quiescence.

The only supported state policy is \textsc{Reset}, and only for candidates whose verifier-produced \texttt{referenced\_map\_handles} is empty. Map-bearing candidates return \textsc{PersistentStateUnsupported} before gate acquisition, and transfer is rejected explicitly. This policy performs no clearing: ``reset'' means the candidate references no runtime maps; it says nothing about physical, device, or external state.

Once gated and quiescent, replacement checks expected identity, ownership, retained load-time authentication provenance, and candidate authorization against the ceiling captured at bootstrap. It reruns TIMER-context verification and checks conflicts and quota; it does not reauthenticate the artifact. Fallible snapshot preparation precedes live mutation. A final emergency-stop check uses the kernel's existing monitor serialization; stop state or lock contention rejects without change. The commit publishes one old-to-new snapshot and fresh epoch together with a receipt and an allocation-free CPU-admission ledger delta of $-\mathrm{cost}(A)+\mathrm{cost}(B)$. Resident-memory charges for both programs persist. Replacement leaves the previous program loaded. Rollback uses the same conditional replacement in reverse with a fresh epoch, provided that program has not subsequently been unloaded.

The primitive deliberately stops at the executor boundary. Receipts and diagnostic guard observations carry installation identity. Production dispatch currently returns a count or error without an identity-bearing audit record. Extending that identity through downstream command queues and actuation audit records is future work. The present scope does not establish command freshness after dispatch, hardware-stop timing, physical safety, controller stability, or state migration.

\section{Prototype and fault-injected publication experiment}
\label{sec:evaluation}
\subsection{Separate evaluation axes}
The evaluation unit is a candidate within a versioned sequence. The task axis asks whether activated candidates improve an independently declared task metric. The installation axis asks whether the publication contract holds. These axes form four possible outcomes: improvement with or without correct installation, and regression with or without correct installation. A useful candidate cannot excuse an installation defect; correct publication cannot establish adaptation quality.

We use hand-written, map-free bytecode candidates in hosted tests of the production kernel library. Fixtures explicitly enable unsigned development loading; the experiment does not test authentication. The embedded admission profile assigns a nominal 1\,kHz hook frequency and a 500\,ms/s aggregate CPU budget. Two unrelated syscall-hook programs consume budget without changing TIMER cardinality. These are admission-model quantities, not measured execution times.

We compare three manager protocols on the same supported scenarios: \textbf{attach-first} (AF), \textbf{detach-first} (DF), and \textbf{transactional replacement} (TX). Each scenario fixes its starting installation, candidate bytecode, and fault location. Stopping after the first API publication leaves a two-step request incomplete; TX completes its single API operation. This is interruption between calls, not crash injection inside commit. Snapshot-allocation failure is injected immediately before candidate snapshot preparation, after predecessor removal for DF. Additional TX-only cases test an outstanding invocation, retry, and stale expected identity; they are excluded from the matched table.

A separate \textbf{component ablation} publishes B through the existing epoch snapshot while retaining an A reader, then acquires a B reader before dropping A. It tests whether single-pointer publication alone prevents overlapping guards; it supplies neither manager accounting nor installation receipts. Host observations hold real production snapshot/invocation guards but do not execute privileged bytecode. We therefore report outstanding guards, not simultaneous motor commands. A QEMU probe separately exercises interpreter dispatch after A--B--A installations.

Python analyzes Rust-emitted observations. Snapshot cardinality counts published program handles; accounting compares the observed ledger against fixture charges pre-measured by standalone manager attachments plus unrelated reservations. A failed request preserves its predecessor only if snapshot, installation identity, and ledger all remain unchanged. Table observations consist of actual intermediate snapshots and the final snapshot for each matched request; setup and restoration are excluded. These finite, deliberately adversarial schedules expose contract failures, not population failure rates.

Cross-compilation and emulator dispatch are software checks; neither establishes physical safety or continual-learning performance.

\section{Limits and research agenda}
\label{sec:limits}
The guarded protocol trades availability for an explicit failure mode: an invocation may be skipped during a transition, and a replacement may have to retry rather than wait. Whether that trade is acceptable depends on the slot period and the controller above it. Likewise, retaining both programs consumes memory, and rejecting map-bearing candidates excludes useful stateful updates. These are visible limits rather than silent state-transfer assumptions.

Kernel placement is a design choice: middleware enforcing the same invocation, identity, authority, state, and accounting contract could provide equivalent semantics. A sufficiently integrated action shield might subsume some installation checks. Our baselines expose uncoordinated attach/detach failure modes; they do not establish superiority over coordinated rollout or hot-swap systems. A stronger comparison should hold those surrounding mechanisms fixed and measure false rejection, availability, and task improvement alongside publication correctness. Maximal rejection is not success: a system that never admits an update can satisfy exclusivity while making continual adaptation useless.

The manager campaign and component ablation can test exclusivity, freshness, fail-closed behavior, and accounting, but it cannot support claims about physical safety. A command already dispatched downstream may outlive the installation that produced it. Closing that gap requires carrying installation identity into command and actuation records and defining where stale commands are rejected. Hardware experiments must separately validate emergency-stop timing, plant assumptions, and safe re-arming.

Adaptation quality also remains unevaluated. Two follow-up scenarios are motor-reflex adaptation after a payload change and sensor-processing adaptation after distribution shift. The former tests actuator authority; the latter tests resource bounds and state compatibility without reducing the problem to an actuator filter. A later learning experiment should hold task streams, budgets, and action-assurance configuration fixed while reporting task outcomes independently from installation outcomes. Candidate generation may then respond to prior activations, so proposal sequences can diverge and must remain attributable. The immediate contribution is smaller: a testable publication contract for one exclusive runtime slot, situated beneath existing lifecycle governance and alongside existing atomic controller-swap systems. For continually learning embodied agents, who guards the update is a question about the execution substrate as well as the learner.
