\begin{abstract}
An embodied agent can improve a controller while remaining unreliable at installing it. Atomic publication selects one current program, but does not by itself prevent old and new invocations from overlapping. We define an executor-level installation contract combining expected installation identity, invocation quiescence, stateless admission, authority revalidation, and resource-atomic publication. A prototype implements this contract for one opt-in runtime slot using a nonblocking transition gate. We compare it with atomic publication sharing the same manager checks, accounting, and receipts, under matched failures and concurrent invocation. Across nine matched scenarios, atomic publication exposes one old/new-guard overlap; guarded replacement exposes none. Both preserve the predecessor on six rejecting requests. Hosted measurements separately quantify replacement and guard costs, retries, skipped dispatches, and retained bytecode. The results concern software installation; closed-loop continual learning, downstream command fencing, and physical safety remain outside the evaluated contract.
\end{abstract}

\section{The update is part of the execution contract}
\label{sec:position}
An agent revises a motor reflex after a payload change. Its candidate passes isolated tests, but activation races an old invocation whose queued command arrives later. A stale recovery request may also replace a newer installation that reuses the same program handle. These are installation failures, independent of controller quality.

Executable skills are one concrete adaptation medium: Voyager, for example, grows a library of programs using environmental feedback \citep{wang2023voyager}. Physical control adds restricted authority, deadlines, and effects that software rollback cannot undo. Our thesis is: \emph{adaptation should not imply deployment}. A candidate becomes authoritative only through a specified transition whose concurrency, identity, state, and accounting rules can be tested.

Qin et al. govern capability versions through compatibility checks, sandbox/shadow evaluation, gated activation, monitoring, rollback, and audit \citep{qin2026governed}. LITHE atomically swaps controller pointers at the end of a Spine cycle: its single loop supplies implicit quiescence, while state persists in shared memory \citep{lim2026lithe}. Kitsune supplies state-preserving dynamic software updating \citep{hayden2014kitsune}. Our narrower question concerns concurrent invocation, resource ownership, and stale requests at an executable hook boundary.

Action assurance is complementary: shielding constrains learner actions \citep{alshiekh2018shielding}, while Neural Simplex combines runtime assurance and online retraining \citep{phan2020neural}. An action monitor asks whether a command may execute; publication determines which installation may issue it. Evaluation should distinguish these obligations.

Our contributions are: (1) an executor-level contract combining expected installation identity, invocation quiescence, state admissibility, authority revalidation, and resource-atomic publication; (2) an implementation for one exclusive slot using a nonblocking transition gate and monotonic epochs; and (3) a comparison with atomic publication sharing the same manager checks, reporting correctness and hosted availability costs separately.

\section{A narrow transactional publication primitive}
\label{sec:semantics}
The prototype is a bare-metal Rust research kernel with verified runtime programs, authenticated load policy, capabilities, quotas, generation-tagged handles, and immutable snapshots. We add one opt-in exclusive TIMER slot. Ordinary TIMER fanout coexists outside its gate: exclusivity concerns this slot, not all hardware access. Here, \emph{transactional} means publication of software authority, without atomic physical effects or persistent recovery.

An installation is identified by
\begin{equation}
 I=(h,e), \qquad e\in\{1,\ldots,2^{64}-1\},
\end{equation}
where $h$ is a program handle and $e$ is a monotonically increasing installation epoch. Replacement is a compare-and-swap-style operation on the expected $I$, not just $h$. It publishes a fresh epoch at every successful replacement, including rollback, so removing and later reinstalling the same handle does not make an old request current (the ABA case). Epoch exhaustion rejects the transition. Bootstrap is a separate operation.

Invocation and replacement share one atomic state: open, active, or transitioning. An invocation atomically claims the open state; a transitioning state returns \textsc{TransitionBusy}, and an active state returns \textsc{ExecutionBusy}. Both failures increment explicit skipped-invocation counters. The invocation holds the immutable snapshot guard throughout execution and drops that guard before reopening the slot. A replacement tries to change open to transitioning once. If an invocation is active, it returns \textsc{Busy} immediately and leaves the slot unchanged; it never waits for quiescence.

The supported policy is \textsc{Stateless}: candidates must have no verifier-reported runtime-map references. Map-bearing candidates and state transfer are rejected before gate acquisition. The internal API retains the enum name \texttt{Reset}, but performs no clearing. This restriction says nothing about physical, device, or external state.

Once gated and quiescent, replacement checks expected identity, ownership, retained load-time authentication provenance, and candidate authorization against the ceiling captured at bootstrap. It reruns TIMER-context verification and checks conflicts and quota; it does not reauthenticate the artifact. Fallible snapshot preparation precedes live mutation. A final emergency-stop check uses the kernel's existing monitor serialization; stop state or lock contention rejects without change. The published immutable object contains both the runtime reference and full installation identity. The serialized manager commits an allocation-free CPU-admission delta of $-\mathrm{cost}(A)+\mathrm{cost}(B)$, publishes that object once, and records the matching receipt before reopening the slot. Invocation readers consume the object; other manager operations cannot observe intermediate ledger or receipt state. Resident-memory charges for both programs persist. Replacement leaves the previous program loaded. Rollback uses the same conditional replacement in reverse with a fresh epoch, provided that program has not subsequently been unloaded.

\paragraph{Two invariants.}
Assume serialized manager operations, normal returns, and invocations that hold their slot guard throughout their body. \emph{Invocation exclusivity:} if replacement from $I_A$ to $I_B$ succeeds, no guarded invocation of $I_A$ overlaps one of $I_B$. Entry claims open$\rightarrow$active; replacement claims open$\rightarrow$transitioning on the same atomic state. These claims exclude one another. Replacement publishes $I_B$ while transitioning, rejects new entries until completion, and reopens only with $I_B$ current. An old reader drops its snapshot before reopening. A successful invocation linearizes at its open-to-active transition; replacement linearizes at the pointer swap of the complete installation object.

\emph{Returned-error preservation:} every replacement returning an error preserves the published installation, executable snapshot, and admission ledger. All rejecting checks and snapshot preparation precede mutation. Ledger commit validates before writing; after it succeeds, publication and receipt updates have no error return. Releasing an unsuccessful transition only reopens the gate. This proposition excludes diagnostic counters, panic/crash recovery, and physical effects.

Receipts and diagnostic guard observations carry installation identity; production dispatch and actuation audit do not yet propagate it downstream.

\section{Correctness and availability under matched updates}
\label{sec:evaluation}
\paragraph{Two evaluation axes.}
The task axis measures whether activated candidates improve a declared task metric; the installation axis checks publication correctness. Improvement cannot excuse an installation defect, and correct publication cannot establish adaptation quality. Fixed candidate sequences isolate the installation axis.

\paragraph{Same-manager comparison.}
The primary protocols are \textbf{atomic publication} (AP) and \textbf{guarded replacement} (GR). They share candidate validation, full expected identity, ownership and authority checks, TIMER re-verification, admission-ledger replacement, snapshot preparation, and receipts. AP bypasses only the invocation gate, through a host-only diagnostic path absent from bare-metal builds. Both publish the same immutable identity/runtime object. AP's epoch mechanism retains the predecessor allocation and waits for old readers before returning, but B becomes visible during that wait. A reader of B can therefore overlap a retained reader of A before replacement returns. GR instead returns \textsc{Busy} while A is active; after A finishes, a retry can publish B. Each fixture fixes its protocol until draining cleanup.

The hosted campaign uses hand-written map-free bytecode and unsigned development loading; it does not test authentication. Real snapshot/slot guards are held through observation callbacks, without executing privileged bytecode or actuation helpers. The admission profile assigns a nominal 1\,kHz hook frequency and a 500\,ms/s CPU budget; unrelated syscall-hook reservations exercise the finite budget. Fixture charges are pre-measured through standalone manager attachments. These charges are admission-model quantities, not measured execution times. A separate QEMU probe checks interpreter dispatch after A--B--A installation and stale-request rejection.

\paragraph{Fault schedules.}
Both protocols receive the same snapshot-preparation failure, over-budget candidate, authority violation, stale expected installation, completed retry, ABA request, rollback, and concurrent-proposer schedules. Snapshot, full identity, ledger, and receipt are checked before and after returned errors. The concurrent-invocation schedule retains an A guard, starts replacement, and attempts a B invocation. AP must expose B before releasing A; GR rejects replacement until A drains. Overlap observations carry the identities captured by the actual guards. We do not read manager accounting from a callback while AP's writer waits for that callback, which would deadlock; accounting is checked before and after the operation.

\paragraph{Hosted cost campaign.}
We use release builds with identical preloaded candidates across both manager paths. A dispatcher and updater are pinned to separate physical cores of an AMD Ryzen 7 7735HS running Linux, with normal scheduling and frequency scaling. Dispatch has an absolute 1\,ms period and requested guard hold times of 0, 10, 100, or 500\,$\mu$s. Hold durations are imposed test conditions, not bytecode runtimes. Per protocol and hold regime, ten fresh processes each perform 1,000 raw replacement attempts after excluded warmup. A deterministic phase sweep spans the dispatch period. A \textsc{Busy} result retains the same logical request; only a successful receipt advances the expected installation and candidate.

\section{Scope and implications}
\label{sec:limits}
Quiescence trades availability for rejection and serializes invocations. Acceptability depends on the controller and schedule; maximal rejection is not success. Retaining predecessors costs memory, and stateless admission excludes useful updates. Equivalent middleware could enforce this contract. Our AP baseline is a manager ablation, not LITHE: a single loop can provide cycle-boundary quiescence without this gate.



The contract ends at the guarded invocation. Commands can outlive their installation; physical motion cannot be rolled back. Queue fencing requires propagated identity and a stale-command rejection point. Controller stability, state transfer, persistent recovery, hardware-stop timing, and continual-learning quality require separate experiments. Motor-reflex and sensor-processing adaptation should report task quality independently from installation correctness: adaptation should not imply deployment.
