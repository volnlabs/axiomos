\section{Protocol API and state machine}
\label{app:protocol}
Installation identity is $(h,e)$, distinct from the two reclamation-reader epochs. An installation epoch increases after every success, including rollback, and never wraps. Bootstrap establishes the authority ceiling. A candidate is a loaded resident program. Original signed artifact bytes are not retained: the runtime stores decoded instructions and load-time metadata, then rechecks verification and authorization at installation.

\begin{quote}\small
\begin{tabular}{@{}l@{}}
\texttt{invoke(callback):}\\
\quad claim open$\rightarrow$active or return \texttt{ExecutionBusy}/\texttt{TransitionBusy}\\
\quad read immutable (runtime, identity); if empty, reopen and reject\\
\quad call callback while retaining the invocation guard\\
\quad drop snapshot pin; reopen; return callback result\\[3pt]
\texttt{try\_replace(owner, expected, candidate, Stateless):}\\
\quad validate candidate and absence of referenced maps\\
\quad claim open$\rightarrow$transitioning or return \texttt{Busy}\\
\quad check expected identity, owner, provenance, authority and conflicts\\
\quad reverify TIMER constraints; preflight accounting delta and next epoch\\
\quad prepare snapshot; acquire final clear-stop gate or reject\\
\quad validate and commit accounting delta\\
\quad exchange immutable (runtime, identity) pointer [linearization]\\
\quad finish publication; set manager epoch, identity and receipt\\
\quad release stop gate; reopen; return receipt
\end{tabular}
\end{quote}

All error exits release any acquired transition guard. Candidate checks precede gate acquisition, so an invalid candidate can return its specific error while another invocation is active. Receipt fields identify slot, predecessor and installed identity. Same-handle rollback is a new installation rather than reversal of time.

QF-AP uses the same commit preparation and accounting. Its diagnostic publication omits the invocation gate: after pointer exchange and reader-epoch flip it waits for the previous reader counter, then reclaims. During that wait, a reader can observe B while manager-protected identity and receipt still describe A; manager access remains serialized and unavailable. Those fields are coherent on return, not co-published. GR has excluded participating predecessor invocations before committing. Production dispatch does not propagate installation identity to downstream actuation.

\section{Assumptions and proof details}
\label{app:proofs}
Assume serialized manager operations, valid use of the opted-in slot, guards retained through callback execution, and normal completion after ledger commit. Exclude unsafe bypasses, ordinary TIMER fanout, panic, power loss and commands escaping the invocation. Rejected operations can change diagnostic counters. Bootstrap and deliberate teardown are outside replacement's nonempty-slot invariant.

\paragraph{Invocation exclusivity.}
Entry and guarded transition claim the same sequentially consistent state from open. Atomic modification order admits at most one. Active excludes publication; transitioning excludes invocation. Rust RAII releases the old epoch reader before reopening, while the transition publishes the successor before reopening. Thus no guarded predecessor invocation overlaps a guarded successor invocation. This is not a command-consumer freshness proof.

\paragraph{Returned-error preservation.}
Candidate, identity, authority, verifier, quota, epoch and allocation checks precede mutation. Final stop-state and lock-contention rejection precede ledger commit. The ledger revalidates before writing; publication and receipt updates afterward have no error return. Consequently a returned error preserves snapshot, installation identity, ledger and last receipt. This argument promises neither crash rollback nor unchanged concurrent skip counters.

\paragraph{Freshness and accounting.}
After $A_{e_1}\rightarrow B_{e_2}\rightarrow A_{e_3}$, the old expected $(A,e_1)$ fails equality with $(A,e_3)$. Epoch exhaustion rejects. Serialized proposers expecting one incumbent have at most one winner; admissibility or a busy gate can leave no winner. Completed-request retries reject rather than act as idempotent acknowledgements. Admission preflight checks $C-c_A+c_B$ before commit. Failed updates leave $C$ unchanged; resident-memory charges for both loaded programs persist independently of the one active-slot charge.

\section{Hosted measurement and complete distributions}
\label{app:measurement}
Both protocols use the same preloaded candidates, 1\,ms dispatcher period and absolute updater phases. Ten fresh processes per hold use 1,000 excluded warmup operations followed by 1,000 measured attempts. Holds are imposed guard durations, not bytecode runtimes. Dispatcher CPU 12 and updater CPU 14 are on separate physical cores of the retained Ryzen 7 7735HS; clock resolution, compiler/release flags, affinity, governor and boost state are recorded in the environment manifest. OS lateness, missed releases and tails remain in the data. The hosted dispatcher executes late releases immediately while lateness is below one period, and expires older releases. Long callbacks can therefore cause near-continuous catch-up occupancy. The replay instead attempts each fixed tick and GR skips active ticks. Their progress results describe different declared arrival policies, not a universal duty-cycle threshold.

Attempt $j$ in process $r$ is scheduled at $t_0+j\,\mathrm{ms}+((137j+97r)\bmod1000)\,\mu\mathrm{s}$. Busy retains the same logical request; success advances its expected identity and candidate. The clock is \texttt{CLOCK\_MONOTONIC\_RAW}. The timed callback stores only the post-swap/epoch-flip clock observation in preallocated storage, before reclamation waiting; no extra observer reader, allocation or logging is inserted. Clock failure invalidates capture without an error return after commit.

For first scheduled release $s$, first API-call entry $a$ (the called timestamp), successful post-swap observation $p$, and API return $r$, derive all four intervals $p-s,p-a,r-s,r-a$. Publication and return must not be substituted. Quantiles use nearest-rank $\lceil qn\rceil$. Aggregate latency cells use median of process quantiles, and the largest observed maximum. They condition on completion rather than assigning a latency to unfinished requests. The started timestamp precedes pre-call setup; scheduled intervals include that setup and initial scheduler delay. \section{Complete control-replay specification}
\label{app:replay}
The primary grid has exactly four holds times 50 phases times two protocols. The separate stress stratum adds 50 phases per protocol at 1,100\,$\mu$s. Each case has a fresh manager, identical resident candidates and an eight-second plant trajectory. Initial velocity and held command are zero; mass is 1 before 4\,s and 2 afterward; $r(t)=(-1)^{\lfloor t/1\mathrm{s}\rfloor}$. Commands are $u=\mathrm{clip}(k(r-v),-4,4)$ and the Euler plant step is
\[
 v(t+\Delta)=v(t)+\Delta\,(u_{\mathrm{held}}-v(t))/m(t),\quad \Delta\leq100\,\mu\mathrm{s}.
\]
The mesh is fixed for the matched protocols from the regular integration grid and every potential attempt and completion time, including suppressed attempts. Protocol-dependent extra Euler subdivisions must not affect task comparisons.

The seed tuner uses preceding 250-tick RMSE, threshold 0.1, initial gain 1 and cap 16, at 4.25/4.5/4.75/5\,s. Its frozen gains are 2/4/8/16. Grid primaries occur at those bases plus phase $p$. Retry $j$ occurs at $b+j\cdot1000+((p+137j)\bmod1000)$\,$\mu$s, only following Busy and strictly before primary+20\,ms. Expired requests are retained. No completed request receives a synthetic retry.

At equal timestamps finish invocations in start order, apply their captured commands, finalize completed QF-AP calls, process attempts, then dispatch. Zero-hold invocation completes immediately. Commands capture identity, reference, velocity and gain at entry; later completion applies the captured value. Skipped dispatch retains output. Observing QF-AP's published identity does not acquire the manager lock held by its pending writer. Cleanup drains all workers, clears the exact final installation, unloads resident handles and checks accounting.

RMSE uses 4,000 ticks before and 4,000 after the mass change, including skipped ticks. Record maximum absolute error/command, saturation at the declared bound and violations above 4 separately. These are simulation envelopes, not physical constraints. Scenario fractions describe a census of the declared grid. Per-request retry/deadline populations differ from the 50-scenario populations; complete CSV rows retain both denominators.

The legacy replay retains its one special 2\,ms hold and paired synchronous 250\,ms utility probes as a separate witness. It is not pooled into the primary grid. No random seed or post-hoc choice is involved.

\paragraph{Corrective case.}
Use mass 1, $v(0)=1$, held command 1, reference 2, gain 1 and a single gain-zero proposal at 4.250\,s. Normal holds are 100\,$\mu$s; one invocation starting at 4.249\,s ends at 4.251\,s. The same retry policy applies. Integrate absolute command over both the common fault-to-8\,s horizon and each publication-to-8\,s horizon; report the latter as different windows. Stop-band entry requires $|v|\leq0.05$ continuously for 100\,ms, with entry and confirmation recorded or censored at the horizon. Post-fault tracking error retains reference 2; the stop criterion instead targets zero velocity. A retired completion is an installation defect even when its task consequence is small or absent.

\section{Conditional comparison with established mechanisms}
\label{app:related}
ROS~2 lifecycle exposes supervised states and managed-processing policies; its design does not specify a linearized drain of in-flight callbacks \citep{ros2lifecycle}. Kitsune obtains all-thread quiescence at explicit update points and transforms state. Livepatch instead converges tasks individually and may remain transitional indefinitely \citep{hayden2014kitsune,linuxlivepatch}. RCU deliberately permits old readers after new publication \citep{linuxrcu}. These mechanisms supply different consistency boundaries rather than interchangeable safety guarantees.

Qin's lifecycle governs whether a version should advance; the exact-incumbent concurrency and accounting protocol is not specified in the procedures inspected \citep{qin2026governed}. Our identity check addresses the established ABA problem; the publication point uses linearizability \citep{michael2004hazard,herlihy1990linearizability}. The contribution is the combined, tested contract and its availability consequences, not invention of those primitives.
