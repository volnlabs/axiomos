\section{Protocol API and state machine}
\label{app:protocol}
The pseudocode below summarizes the existing guarded replacement API. A candidate is a resident, loaded program handle; installation identity $I=(h,e)$ also contains a monotonically increasing epoch. Bootstrap installs into an empty slot and establishes its authority ceiling; replacement requires an expected predecessor identity. Rollback is replacement with the retained predecessor handle and a new epoch. Neither operation restores physical history.

\begin{quote}
\begin{tabular}{@{}l@{}}
\texttt{try\_replace(owner, slot, expected, candidate, Stateless):}\\
\quad validate resident candidate and absence of referenced maps\\
\quad acquire open$\rightarrow$transitioning, or return \texttt{Busy}\\
\quad check current identity, ownership, provenance and authority\\
\quad reject attached/in-use candidate; reverify TIMER constraints\\
\quad preflight admission delta; check next epoch; prepare snapshot\\
\quad acquire final emergency-stop gate, or return an error\\
\quad commit admission delta, validating before any ledger write\\
\quad publish immutable (runtime, identity) snapshot \emph{[linearization]}\\
\quad update manager identity, epoch and receipt; release stop gate\\
\quad reopen slot; return receipt
\end{tabular}
\end{quote}

All error exits after acquisition release the transition guard. Candidate validation precedes gate acquisition: a bad candidate need not receive \texttt{Busy} even when an invocation is active. The resident entry contains decoded instructions and load-time provenance, not original signed artifact bytes. Replacement re-verifies those instructions and authorization; it does not reauthenticate a source artifact or reevaluate trust-store membership.

Invocation claims open$\rightarrow$active on the same sequentially consistent atomic state, then reads the immutable installation. The successful claim is its linearization point. A claim against active yields \texttt{ExecutionBusy}; against transitioning it yields \texttt{TransitionBusy}. An empty snapshot reopens the slot and returns \texttt{Empty}. On completion, the guard drops its epoch reader \emph{before} returning the state to open. Transition-guard destruction similarly releases its reader before reopening.

\section{Proof details}
\label{app:proofs}
The following statements concern the opted-in slot. Assume serialized manager operations, invocations retaining their guard throughout their body, and normal completion after ledger commit. They exclude panic, power loss, unsafe bypasses, ordinary TIMER fanout, and downstream queued commands. Diagnostic counters may change on rejection. Bootstrap and intentional teardown are separate from replacement's nonempty-slot invariant.

\paragraph{Invocation exclusivity.}
The only successful entry is open$\rightarrow$active, and the only guarded publication path first claims open$\rightarrow$transitioning. Atomic modification order excludes simultaneous successful claims. While active, publication cannot acquire the gate; while transitioning, new invocation entry fails. The last old guard releases its epoch reader before reopening. The new snapshot is published before the transition reopens. Thus no guarded invocation of the predecessor installation overlaps a successor invocation.

\paragraph{Returned-error preservation.}
Candidate, identity, authority, verification, quota, epoch, and snapshot-preparation checks precede mutation. The final stop gate rejects active stop state or lock contention before ledger commit. Ledger commit validates its preflight token before writing. After a successful ledger write, snapshot publication and manager receipt updates have no returned-error path. Consequently every returned error preserves the executable snapshot, installation identity, ledger, and last receipt. This does not promise that concurrent dispatch attempts avoid skip-counter increments.

\paragraph{ABA rejection and one winner.}
After $A_{e_1}\rightarrow B_{e_2}\rightarrow A_{e_3}$, the old expected pair $(A,e_1)$ differs from $(A,e_3)$. Epoch increment is checked rather than wrapping. A stale request therefore cannot become current by handle reuse. For two otherwise admissible proposers expecting the same installation, serialized manager operations let the first successful replacement advance identity; the other receives \texttt{StaleInstallation}. At most one wins; without quiescence or admissible candidates there may be no winner. Repeating a completed request is rejected, not acknowledged as an idempotent success.

\paragraph{Resource accounting.}
For admitted slot charge $c_A$ and candidate charge $c_B$, preflight validates the prospective total $C-c_A+c_B$, including arithmetic and budget constraints. Commit revalidates before applying the delta. Failed replacement leaves $C$ unchanged, while successful replacement charges exactly one slot installation. This slot charge is distinct from resident-memory accounting: both loaded programs remain charged while retained. Holding the manager serialization boundary across ledger commit and publication prevents another manager operation observing their intermediate state.

\section{Hosted measurement methodology}
\label{app:measurement}
The retained host is an AMD Ryzen 7 7735HS with eight physical cores and two hardware threads per core. Dispatcher CPU 12 and updater CPU 14 belong to different physical cores (6 and 7); their siblings are 13 and 15. The recorded governor is \texttt{performance}, boost is enabled, and neither frequency nor scheduler latency is fixed. The build uses Rust 1.98.0-nightly dated 2026-07-01, LLVM 22.1.8, the Linux x86-64 host target, and Cargo's release test profile. Bare-metal target flags do not describe these host tests. Sanitized recorded build information accompanies the traces.

Each protocol/hold regime has ten new processes. Each process performs 1,000 uncontended warm-up replacements, then 1,000 measured attempts. Invocation holds are 0, 10, 100, or 500\,$\mu$s; dispatcher period is 1\,ms. Updater attempt $j$ in run $r$ is scheduled at
\[
 t_0+j\cdot1\,\mathrm{ms}+((137j+97r)\bmod1000)\,\mu\mathrm{s}.
\]
This deterministic sweep varies phase without claiming randomized independence. \texttt{CLOCK\_MONOTONIC\_RAW} reports 1\,ns resolution; clock measurement overhead remains included. Samples are buffered before JSON emission. Late dispatches and missed releases are retained, not removed as outliers. Quantile $q$ uses sorted sample rank $\lceil qn\rceil$, including the lower middle observation for an even-sized median. Requested holds differ from observed guard durations; host observer timings exclude privileged bytecode execution.

\paragraph{Logical-request elapsed time.}
Group attempts by protocol, hold, process and logical-request number; numbering restarts in each process. For a completed request, compute
\[
 L= t^{\mathrm{start}}_{\mathrm{last}}+\ell_{\mathrm{last}}-t^{\mathrm{start}}_{\mathrm{first}},
\]
where $\ell$ is measured API-call latency and the last attempt returns \texttt{Ok}. This includes earlier \texttt{Busy} calls, retry waiting and inter-attempt scheduler delay. It excludes initial lateness before the first actual call. It measures first-attempt-to-success under this retry schedule, not agent proposal-to-actuation latency. For AP, each request has one attempt, so $L$ equals successful-call latency.

\section{Control-replay specification}
\label{app:replay}
Initialize $v(0)=0$, held command $u=0$, and gain $k=1$. Over $0\leq t<8$\,s, use $m(t)=1$ before 4\,s and $2$ thereafter, with $r(t)=(-1)^{\lfloor t/1\mathrm{s}\rfloor}$. At 100\,$\mu$s integration steps,
\[
 v_{n+1}=v_n+10^{-4}(u_{\mathrm{held}}-v_n)/m(t_n),\qquad
 u=\mathrm{clip}(k(r-v),-4,4).
\]
At each step, finish due invocations in start order and apply their captured commands; finalize any completed AP replacement; process update attempts; process a control tick when due; then integrate. Control ticks are 1\,ms apart. Commands capture gain, identity, reference and velocity at invocation entry. They become the held output only at completion. A skipped tick preserves the previous command. Multiple completions at one timestamp are applied in their recorded order.

The seed tuner observes the preceding 250 control-tick squared errors, before the current tick. At 4.25, 4.5, 4.75 and 5\,s it doubles the current gain, capped at 16, if window RMSE exceeds 0.1. This yields the frozen proposals $2,4,8,16$. The seed trajectory uses synchronous controller evaluation; proposal generation is separate from all three installation-conditioned replays. No random seed is needed: the plant, proposal times, gains and logical schedules are deterministic.

Normal invocations hold a real runtime guard for 100\,$\mu$s of simulated time. One invocation starting at 4.249\,s holds it until 4.251\,s. Every proposal has a primary attempt and a fixed $+1$\,ms event. Under AP the first new installation publishes at 4.250\,s while the predecessor invocation is live, allowing a new invocation. At 4.251\,s the predecessor's captured command is applied after publication, producing the one retired-command observation. Under GR the primary attempt returns \texttt{Busy}; the old invocation finishes before the retry publishes the successor. Frozen uses the same serialized entry gate but makes no replacements, hence its single skipped tick during the injected long hold.

Tracking RMSE uses 4,000 ticks in $[0,4)$\,s and 4,000 in $[4,8)$\,s, including ticks whose invocation is skipped. For each actual activation, the paired utility probe clones the current plant velocity and time, then evaluates predecessor and candidate gains separately for 250\,ms with synchronous control updates, the same reference/mass schedule, and the same Euler integrator. Lower candidate RMSE marks that activation useful. These probes omit invocation delays and are local counterfactuals, not independent deployment trials. Programs encode gain constants; real manager installations select their identity, while host arithmetic computes commands. Neither the plant nor command application is physical actuation.

\paragraph{Extended related work.}
SENTINEL checks semantic interpretation, plans and execution trajectories against temporal-logic safety specifications \citep{zhan2025sentinel}. Such checks can complement an installation contract: they ask whether requirements and behavior satisfy safety properties, while publication governs which installation may issue requests. This paper demonstrates neither SENTINEL integration nor those physical-safety properties.

RCU separates publication from reclamation: a new pointer can become visible while pre-existing read-side critical sections retain an old allocation; a grace-period wait protects subsequent reclamation \citep{linuxrcu}. Our AP witness uses an epoch snapshot with this distinction, not Linux RCU as an experimental baseline. Quiescence and pointer exchange are established mechanisms. The contribution here combines invocation exclusion with expected installation identity, state admissibility, authority revalidation, resource-atomic accounting and measured availability outcomes at one executor slot. ABot-AgentOS and EmbodiedGovBench motivate adjacent agent-runtime and evaluation concerns; neither is evaluated as an integrated component of this prototype.
