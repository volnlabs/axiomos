# Shrike-lite FPGA safety envelope

`shrike_safety_gate.sv` is the v0.4 reference for the final motor-PWM authority
implemented in the ForgeFPGA project. The FPGA generates PWM from accepted
signed command magnitudes; the retained `*_pwm_in` pins are ignored.

## Integration contract

- `estop_n`: physical latching e-stop line, active low, routed directly to the
  ForgeFPGA input. It must not be generated by RP2040 firmware.
- `rst_n`: runtime reset on FPGA GPIO18/package pin 9, driven by RP2040
  GPIO14. It is separate from package pin 11 PWR, which clears configuration.
- `left_duty_permille` / `right_duty_permille`: signed 12-bit copies of the
  RP2040's commanded motor setpoints, in `-1000..=1000` per-mille units.
- `left_pwm_in` / `right_pwm_in`: retained as ignored RTL compatibility ports,
  with no physical assignments. GPIO14 on the RP2040 now owns runtime reset.
- `*_pwm_out`: the only signals connected to the two motor-driver enable
  inputs. Do not route the RP2040 PWM around this gate.
- `*_direction_out`: FPGA-owned polarity from the accepted signed command;
  negative is high and nonnegative is low. Both force low whenever drive is
  gated. The selected pins are listed below; continuity remains unverified.

One invalid command disables both motors; this avoids allowing one wheel to
continue driving after an envelope violation. Direction pins need not be
gated because PWM-low disables the H-bridge output.

E-stop assertion forces both outputs low combinationally. Deassertion passes
through two clock-domain synchronizer stages and remains disarmed until a
fresh, complete motor transaction begun after that qualification is accepted.
The production defaults state a 50 MHz FPGA clock and 20 kHz PWM carrier; both
parameters require measurement and motor-driver validation on assembled
hardware. Configurations producing zero or more than 100,000,000 carrier
cycles fail closed. Magnitude scaling reduces the constant period/1000 ratio
and sizes the product to its range, preserving integer-floor behavior without
the former 64-bit divider.

## Clock and board assignments

The project registers `ffpga/timing-constraints/clk_50mhz.sdc`:

```tcl
create_clock -name clk {clk} -period 20.000 -waveform {0 10.000}
```

This constrains timing analysis; `CLOCK_HZ` and the SDC do not set the physical
oscillator frequency. `clk` remains OSC_CLK on West Input0, with oscillator
enable asserted and `clkbuf_inhibit` retained as required by the
[Forge Workshop guide](https://www.renesas.com/en/document/gde/forgefpga-workshop-user-guide).
The direct-port-without-CLKBUF warning must be reviewed against that dedicated
clock mapping; do not insert a generic Xilinx buffer to silence it.

For a separate robustness build, replace the registered constraint with
`clk_18ns_guard.sdc` (18 ns, 55.556 MHz). Never load both clocks on `clk`.
Run it at the typical corner and both temperature extremes of the slow and
fast corners. Require actual constraint readback, setup/hold/pulse-width reports
and completed routing; an achievable-frequency estimate alone is insufficient.
The [SLG47910 datasheet](https://www.renesas.com/en/document/dst/slg47910-datasheet)
specifies up to 54.110 MHz at its stated oscillator test conditions, including
2.5 V VDDIO. The R0.4 board uses 3.3 V VDDIO: this guard is a robustness target,
not frequency certification. Input duty-cycle/jitter and asynchronous SPI,
reset and e-stop interface timing require separate qualification. No blanket
false-path or multicycle exceptions are applied.

### Constrained build results — 2026-09-12

Fresh Forge 6.55.001 builds pass post-route setup at the registered **20 ns
(50 MHz)** nominal clock and at the separate **18 ns guard in all five installed
corners**. Nominal typical-corner WNS is **+9.710 ns**; the worst guard WNS is
**+0.300 ns** at the slow 85 °C corner. Every final build has zero failing setup
endpoints, uses **114/140 CLBs**, and generated a bitstream. Reports confirm the
actual period/corner and all 17 active pin assignments against the source project.

The RTL precomputes byte checks, CRC and payload destinations during SPI
reception, and uses predicted PWM wrap and segmented watchdog carry. It preserves
command/status latency, replay history, exact timeout and asynchronous safety
shutdown. Exhaustive range/PWM checks, baseline differential simulation, mapped
simulation and a smoke test of the actual production netlist pass.

Use the checked-in project settings: classic ABC, hard-mux inference disabled,
control LUTs preserved during mapping then flattened before EDIF, and compiler
`-TIMING_DRIVEN_PACKING_THR 0.8`. Different mapping/packing settings require fresh
simulation and timing evidence. Timing qualification covers the production
parameters; changing clock/PWM calibration or timeout requires rebuilding.

Final exported timing reports contain setup results only. Positive hold slack
in the placement-estimated report does not establish post-route hold or pulse
width compliance. Physical clock measurement, continuity, recovery and runtime
qualification remain open. Nothing was programmed. See the
[bench execution record](../../../docs/plans/active/shrike-fpga-bench.md) for the
complete matrix, reproducible checks and fresh nominal project location.

## Post-commit status read

After ending a 12-byte motor command transaction, use a separate SPI mode-0
transaction: send `A5 00` under one chip-select assertion. MISO returns the
status byte during `A5`, then the last accepted sequence during `00`. The two
bytes are a coherent snapshot from the synchronized chip-select event. Hold
chip select low for at least four FPGA clock rising edges before the first
SPI clock rising edge so that snapshot is loaded; this is a protocol timing
requirement, independent of any unvalidated board SPI frequency. Short, long, malformed,
or repeated status reads do not change duties, validity, watchdog state, or
e-stop rearm. Status confirms command acceptance, not physical motor movement.

The default maximum is ±800 per-mille. Any change requires matching the kernel
actuation envelope and validating the final pin assignment on the assembled
robot. The repository now pins the Shrike-lite V1.0/R0.4 electrical source and
MCU interconnect, but the external `estop_n` and motor-output FPGA pins still
require ForgeFPGA I/O-planner agreement and powered-off continuity review.

## Simulation

Run the self-checking testbench with either available simulator:

```sh
iverilog -g2012 -s tb_shrike_safety_gate -o /tmp/shrike_safety_gate.vvp \
  firmware/shrike/fpga/shrike_safety_gate.sv \
  firmware/shrike/fpga/tb_shrike_safety_gate.sv
vvp /tmp/shrike_safety_gate.vvp
```

or:

```sh
verilator --binary --timing --top-module tb_shrike_safety_gate \
  firmware/shrike/fpga/shrike_safety_gate.sv \
  firmware/shrike/fpga/tb_shrike_safety_gate.sv
./obj_dir/Vtb_shrike_safety_gate
```

## Vendor RTL preflight

From the repository root, run the Renesas-bundled Yosys against the checked-in
structural check (replace `yosys` with the installed compiler path):

```sh
yosys -s scripts/verify/fpga-safety-preflight.ys
yosys -s scripts/verify/fpga-mapping-preflight.ys
```

This checks hierarchy, process lowering, conflicting drivers, undriven wires,
logic loops, inferred latches and asynchronous set/reset emulation. The second
check runs the GUI's Xilinx intermediate mapping, rejects mapped latches and
checks that carry blocks alone do not exceed the tile's 140 logic CLBs. This is
only a necessary capacity check: Forge must still check all resources, carry
chain length, placement, routing and timing. Neither check qualifies pins or
produces a Forge bitstream.
The local installed runner and remaining board gates are recorded in the
[bench plan](../../../docs/plans/active/shrike-fpga-bench.md).
